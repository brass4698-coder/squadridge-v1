Identity & verification

Verified pseudonymous accounts

What is implemented

Accounts are persistent, even in anonymous-auth flows. Verification is designed to avoid sharing raw identity attributes in-room, but it is not the same as “no server-side identity.”

Semaphore proofs are verified server-side and tied to the logged-in account in the current release.

What reviewers should confirm

Confirm which verification mode is used for the deployment, whether any demo flags are off, and how the partner will communicate verification and identity boundaries to participants.

Data paths

Transit & storage (current release)

↔
In transit

Standard TLS between client and service — treat as baseline transport protection.

▣
At rest

Message payloads are encrypted before storage with application-layer AES-GCM. Squad-scoped keys remain in the current system and therefore privileged operator paths still matter.

Exact algorithm, key-storage, and access-path details live in the threat model and encryption-scope docs; avoid abbreviating them into marketing shorthand.

Access control

Squad keys & gating

Each squad has a symmetric message key. That keeps plaintext out of casual storage views, but it is not the same as operator-blind E2EE and it has to be reviewed as part of the trusted system.

  • The current release stores squad keys in the system and does not offer forward secrecy or a full key-rotation story.
  • Threat review should include moderator access, service-role access, legal process, and any export or backup paths.

Operator visibility

Explicit, disclosure-consistent

Moderators, service-role paths, and raw database or dashboard access remain material in the current trust model. SquadRidge does not claim that operators are technically unable to read stored messages when moderation, legal process, or incident response requires access.

Mirror this language in every external artifact—never upgrade the current architecture into “server-blind” or “Signal-grade” copy.

Operational reality

Logging & retention (posture)

Structured logs, error telemetry, and moderation audit trails are in scope for review. Logging should be treated as part of the threat model, and retention commitments should be written per deployment rather than implied by a generic slide.

Honest limits

Known limitations (current release)

  • Per-user E2EE where the server never holds decryptable content is not part of the current release.
  • Broad self-serve launch for high-risk populations is not the safe posture today.
  • Any roadmap toward stronger privacy guarantees or CSI scale-up should be labeled roadmap, not “shipping today.”
